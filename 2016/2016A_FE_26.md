# 2016A_FE_26
When new naming conventions for data items are provided, which of the following problems cannot be avoided only by the naming conventions described below?

[Naming conventions]
(1) Always add a classification word such as the “name”, “code”, “number”, “amount”, or “date” at the end of the data item name, and set the data type determined for each classification word.
(2) Create a dictionary in which data item names and their meanings are registered, and ensure that synonyms and homonyms do not occur.

a) Both the date type and the character string exist together as the data type of the data item “ReceiptDate”.
b) It cannot be determined whether the data item “Customer” is the “CustomerCode” or “CustomerName”.
c) The scope of the possible values of the data item “OrderAmount” varies according to the table.
d) There is a data item called “AwardAmount” that has the same meaning as the data item “BonusAmount”.
?
c) The scope of the possible values of the data item “OrderAmount” varies according to the table.
### Explanation
Let's analyze how the given naming conventions address each potential issue:

1. **Convention (1):** Appending a classification word (`name`, `code`, `number`, `amount`, `date`) to the end of each data item name and defining a uniform data type for each classification word:
   - Prevents **a)**: Because `ReceiptDate` ends with `Date`, its data type is uniquely determined. Inconsistent data types (such as having both `DATE` and `VARCHAR`) are prevented.
   - Prevents **b)**: Bare names like `Customer` are disallowed because every item must end with a classification word (e.g., `CustomerCode` or `CustomerName`), resolving ambiguity.

2. **Convention (2):** Registering data item names and meanings in a centralized data dictionary to avoid synonyms and homonyms:
   - Prevents **d)**: Using different names for the identical semantic concept (synonyms like `AwardAmount` vs. `BonusAmount`) is detected and prohibited by the dictionary.

3. **Why c cannot be avoided:**
   - The **scope of possible values** (domain constraints, allowable ranges, minimum/maximum limits, or precision rules) defines the valid values an attribute can take in a specific table or context.
   - Naming conventions standardize attribute **names** and broad **data types** (e.g., standardizing that all `amount` fields are numeric). However, they do not enforce specific domain value constraints across different database tables (e.g., one table might allow `OrderAmount` up to 10,000 while another allows up to 10,000,000).
   - Domain constraints and business validation rules must be defined via database constraints (such as `CHECK` constraints or domain definitions), not naming conventions alone.
   - Therefore, problem **c)** cannot be avoided solely by these conventions.
