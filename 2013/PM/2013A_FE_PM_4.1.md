### Explanation
In public-key cryptography and digital signatures, the encryption and verification processes follow specific steps to ensure confidentiality, authenticity, and non-repudiation.

**Encryption and signing by Sender:**
1. Generate the message digest of the plain message (`m1`) using a message digest function (`MD`). This results in `md1`.
2. The digital signature (`ds`) is created by encrypting the message digest (`md1`) using the **Sender's Private Key**. Looking at Figure 1, the sender generates `ds` using `md1` and blank **B**. Therefore, blank **B** must be the Sender's Private Key (`spk`), which corresponds to choice **c**.
3. The plain message (`m1`) is encrypted for confidentiality using the **Receiver's Public Key**. In Figure 1, `c` is generated using `m1` and blank **A**. Therefore, blank **A** must be the Receiver's Public Key (`ruk`), which corresponds to choice **b**.
4. Both the encrypted message (`c`) and digital signature (`ds`) are transmitted over the unsecured network to the receiver.

**Decryption and verification by Receiver:**
1. The receiver decrypts the encrypted message (`c`) using their own private key (the Receiver's Private Key, `rpk`) to get the received plain message (`m2`).
2. To verify the signature, the receiver must independently generate a message digest (`md2`) of the received message (`m2`) using the same message digest function (`MD`). Therefore, blank **D** is the operation `md2 ← MD( m2 )`, which corresponds to choice **d**.
3. The receiver decrypts the received digital signature (`ds`) to retrieve the sender's original message digest (`md3`). This requires the **Sender's Public Key**. In Figure 1, `md3` is generated by decrypting `ds` using blank **C**. Therefore, blank **C** must be the Sender's Public Key (`suk`), which corresponds to choice **d**.
4. Finally, the receiver compares `md2` and `md3`. If they match, the digital signature is verified, meaning the message truly came from the sender and hasn't been tampered with.

**Why the other choices are incorrect:**
*   **For A, B, and C:** 
    *   `rpk` (Receiver's Private Key) is only known by the receiver and used to decrypt incoming messages.
    *   `spk` (Sender's Private Key) is only known by the sender and used to sign messages. Using it to encrypt the message body (`c`) would fail to provide confidentiality, as anyone with the sender's public key could decrypt it.
    *   `ruk` (Receiver's Public Key) is public and used by anyone wanting to send a confidential message to the receiver.
    *   `suk` (Sender's Public Key) is public and used by anyone to verify the sender's digital signature.
*   **For D:** 
    *   `md2 ← DSE( m2, suk )` and `md2 ← E( m2, suk )` incorrectly attempt to encrypt the message again rather than generating a digest using the `MD` function. Message digests must be generated using a hashing function, not an encryption function.
    *   `md2 ← E( m2, rpk )` incorrectly uses public-key encryption with the receiver's private key instead of a hashing function.
