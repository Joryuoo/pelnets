# 2022S_FE_AM_28

![[2022S_FE_AM_Q28_full.png]]

a)  row row
b)  row table
c)  table row
d)  table table A B
?
c) table row
### Explanation
The question deals with **lock granularity** in a Relational Database Management System (RDBMS). Lock granularity refers to the size of the data item that is locked during a transaction to ensure concurrency control (e.g., row, page, table).

Let's evaluate the trade-offs between **row-level locks** and **table-level locks**:

### Lock Contention (Blank A)
- **Table-level lock:** Locks the entire table. If Transaction 1 is updating a single row, Transaction 2 cannot update *any other row* in the same table until the lock is released. 
- **Row-level lock:** Locks only specific rows. Transaction 1 and Transaction 2 can safely update different rows in the same table simultaneously.
- **Conclusion:** **Table-level locks** cause significantly higher lock contention because they aggressively block access to completely unrelated data within the same table. Thus, Blank A is **table**.

### Memory Overhead (Blank B)
- **Table-level lock:** The RDBMS only needs to maintain a single lock record in memory to manage the entire table.
- **Row-level lock:** The RDBMS must track and manage a separate lock record in memory for *each individual row* that is being updated. If a transaction updates 10,000 rows, it generates 10,000 lock records.
- **Conclusion:** **Row-level locks** consume significantly more memory resources to track and manage. Thus, Blank B is **row**.

### Summary Table

| Granularity | Lock Contention | Concurrency | Memory Overhead |
|---|---|---|---|
| **Table-Level** | High (More likely) | Low | Low |
| **Row-Level** | Low | High | High (Requires more area) |

Therefore, the appropriate combination is A = **table**, B = **row**, which corresponds to option **c**.
