For **Subquestion 2**, the system is modified to allow multiple `Promotion` records for the same `EmpID`. This requires a logic change so that multiple updates can be applied to the same `Old_PayData` record before it is written to the new file.

In the original flowchart's `=` branch (where `Old_PayData.EmpID == Promotion.EmpID`), the program did the following:
1. Process Box (1): `Update Old_PayData with Promotion data`
2. Process Box (2): `write New_PayData`
3. Process Box (3): `Read_Old_PayData`
4. Unnumbered Box: `Read_Promotion`

To handle duplicates, when a match (`=`) is found, we should **only** update the current `Old_PayData` record in memory and then read the next `Promotion` record. We **must not** write to `New_PayData` yet, and we **must not** read the next `Old_PayData` record, because the next `Promotion` record might belong to the same employee. 

Instead, the writing and reading of the next `Old_PayData` record will naturally occur later when the loop encounters the `<` branch (i.e., when all promotions for the current employee have been processed and the next `Promotion` record's ID is finally greater than the current `Old_PayData` ID). 

Therefore, we must remove Process Box (2) (`write New_PayData`) and Process Box (3) (`Read_Old_PayData`) from the `=` branch. This corresponds to Choice **b**.
